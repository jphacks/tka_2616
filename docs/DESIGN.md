あわもん — 統合プロダクト・技術設計書 v0.3
作成日：2026-10-17　｜　状態：MVP実装用ドラフト
0. この設計で決定したこと
- 価値の中心：食器洗いが「かわいい水の妖精と池を育てる体験」に変わること。AIの精度はこの体験を補助する技術である。
- 端末：スマートフォン向けPWA。フロントエンドNext.js/TypeScript、バックエンドFastAPI/Python。
- 画像理解：OpenAI Responses APIで洗浄前後の画像比較。モデルIDは設定ファイルから指定する（初期候補 gpt-6-luna、利用可能性と画像・構造化出力対応を実装時に公式APIで確認）。
- 物体検出：YOLOE-26は任意の補助モジュール。初回MVPの必須依存にはしない。
- 絵作り：キャラクターデザインを選定・凍結してから、パレット固定のドット絵アニメーションを制作する。実行時に画像生成APIを呼ばない。
- 完成順序：①可愛いキャラクターを試作して選ぶ → ②キャラの反応と育成を触れる状態にする → ③カメラ＋OpenAI連携 → ④YOLOE併用実験。
1. プロダクト概要
1.1 コンセプト
洗う前の食器を撮影し、実際に食器を洗い、洗い終えた状態を撮影すると、AIが視覚的変化を分析。ユーザーが食器洗いを完了したことを記録でき、水の妖精「あわもん」が喜び、水滴を使って小さな池が育つ。
1.2 MVPの成功条件
1. 初見で「かわいい」「食器洗いをして反応を見たい」と感じられる。
2. ホームから撮影、完了確認、報酬演出まで迷わず進める。
3. AIが断言できない写真を無理に「洗浄済み」と判定しない。
4. 同じセッションから水滴が二重付与されない。
5. 再起動しても池とキャラクターの成長が保持される。
1.3 対象と非対象
対象：個人の日常的な食器洗いの習慣化。非対象：衛生検査、洗浄証明、監視、厳格な不正検知、洗剤使用の実証。
2. 体験設計
画面	表示	ユーザー操作	アプリ側の動作
Home	池、あわもん、しずく、成長進捗	「食器を洗う」	idleアニメーション再生

- 説明は「皿が減りました」より「シンクが片付きました」のように自然で具体的に表示する。
- 同じ食器の位置移動だけでは洗浄を証明しない。判定が不確実でもユーザーが自己申告で完了を記録できる。
- 洗わなかったことに罰は与えず、キャラクターは死亡・退化しない。
3. キャラクター／ビジュアルデザイン（最重要）
3.1 可愛さは生成手段ではなく、デザインレビューで担保する
AI画像生成やSkillの導入だけでは可愛さを保証できない。静止画コンペ → デザイン固定 → アニメーション検証 → 小規模評価を必須ゲートとする。無条件の「かわいい保証」はできないが、選定基準と再現性を設ける。
3.2 デザインブリーフ
- キャラ：水滴と泡の間にある、丸くてやわらかい水の妖精。
- 性格：嬉しいと跳ねる、控えめで応援上手、失敗時も責めない。
- 形：2〜3頭身というより単純な球・水滴形の短いシルエット。小さな手、必要最小限の足。
- 顔：顔の面積を広く確保し、目・口は少数ピクセルで感情を読めるようにする。
- 色：水色・青緑主体、クリーム白のハイライト、濃い青の輪郭、ほのかな桃色の頬。本体は最大12〜16色（透明を除く）のパレットを基本とする。
- 印象：丸い、柔らかい、清潔、安心感、幼すぎず親しみやすい。
- 禁止事項：過剰な描き込み、フレームごとの目・輪郭の崩壊、表情が読めないほど小さい顔、ぎらつく過剰エフェクト。
3.3 静止画候補と選定
同じ64×64原寸（表示時整数倍拡大）で最低4案を制作する。
A. しずく型（頭の先が水滴）
B. ぷにぷに泡型（ほぼ丸、泡の冠）
C. 水まんじゅう型（平たい半球）
D. 小さな水精霊型（短い手足と葉・泡のアクセント）
各案について、透明背景の正面立ち絵、48px等価の縮小表示、単色シルエット、顔アップを作成。候補を並べ、まず人間が1案を採用する。採用後にデザインマスター（輪郭・顔の配置・色コード・光源方向・基準座標）を凍結する。今あるv0.1ドット絵試作は技術検証用であり、デザインマスター確定版ではない。
3.4 可愛さの評価ゲート
5〜10名程度で簡易A/B選好評価を実施する（数が少ないため統計的な一般化はしない）。無作為順序で候補を提示し、①可愛さ（5段階）②愛着（5段階）③育てたいと思うか（5段階）④小さく表示して見分けられるか、を収集。最上位候補について追加ヒアリングをする。本格的な制作前の確認と位置付ける。
3.5 アセット仕様
- ベースキャンバス：64×64 RGBA（透明背景）、ドットは整数グリッド。
- 表示：CSS image-rendering: pixelated、整数倍スケーリングを基本とする。
- スプライトごとの原点・足元アンカーを固定。感情表現で目や輪郭が不自然に漂わないこと。
- マスターデータは assets/awamon/master/ に置き、生成元スクリプトと配色表もGit管理。
- アセット形式：各状態のスプライトシートPNG + フレーム幅・高さ・所要時間・原点のJSON。プレビューGIFは確認用であり、アプリ本体ではPNGスプライトを優先。
4. ドット絵アニメーション
4.1 初期状態（MVP）
状態	役割	目安	注意点
idle	通常・ホーム	6〜8フレーム、約1〜1.5秒	呼吸・まばたき、自然な無限ループ
happy	洗浄記録・報酬	8フレーム、約0.8〜1.2秒	跳ね・笑顔・泡の粒、発動時に1〜2回
sleep	夜・しばらく放置	4〜6フレーム、約1.5〜2.5秒	穏やかな呼吸、威圧的な催促なし
grow	池のレベルアップ	8〜12フレーム	しずくの落下、水面の波紋、キャラの喜び


公開時点ではidle / happyの2状態を必須とし、sleep / growは次段階に回してもよい。食器洗い専用のため eat は初期状態に含めない。
4.2 モーションの分担
- 表情・体形変化：ドット絵のフレーム差し替え。
- 画面上の微小な上下浮遊：JS/CSSで整数ピクセル単位の移動。
- 水滴・泡・波紋：キャラ本体とは別レイヤーで再生（パーティクル数は制限）。
- 進化：キャラクターを毎回生成し直さず、基本は池・背景・装飾の恒久的変化で表現する。
4.3 Skill活用方針
pixel-art-studio（https://github.com/Gamezxz/pixel-art-studio）：Python/Pillowでドット絵の生成・差分管理・スプライトシート・GIFを書き出す制作手順。ソースを再実行可能に保持し、3回程度の「描画→目視→修正」ループを作業基準とする。
pixel-anims（https://github.com/dris1153/pixel-anims）：Canvasベースのループアニメーション制作用。アニメーション表現の試作や参考に使う。**最終のキャラは固定マスタースプライトを再利用**し、Skillごとにデザインを変えない。
pixel-plugin（https://github.com/willibrandon/pixel-plugin）：Asepriteによる手修正が必要な場合の予備案。
Skillは制作ワークフローであり、見た目の品質を自動保証するものではない。外部Skillを導入するときはリポジトリのコード・スクリプト・依存関係を確認する。第三者SkillにAPIキーや個人情報を渡さない。
4.4 制作・検査パイプライン
1. 設計マスターを確定しパレット・アンカーを固定。
2. マスターに基づいて各モーションの描画スクリプトを作る。
3. 1x PNG、8xプレビュー、スプライトシート、GIFを書き出す。
4. 人間が各フレームを確認して「顔の位置・同一性・動きの可愛さ・過度なフラッシュ」を採点。
5. 自動チェック：全フレーム同寸、色数予算、透明アルファ、アンカー、ファイル存在、フレームレート、ループ端の差分。
6. スマホの実寸相当（64〜128 CSS px程度）で確認。
7. 承認したアセットにバージョンを振り、以後はコード変更で自動再生成可能にする。
4.5 v0.1試作品の扱い
前回作成した64×64・idle/happy各8フレームのGIF／PNG／生成コード一式は技術検証として保持する。完成品の造形はまだ承認していない。今回の設計の「採用すべきキャラ」ではなく、フレームの書き出し・ループ動作・アプリ組み込みのテスト用フィクスチャとして扱う。
5. AIによる食器洗い判定
5.1 OpenAI（ベースライン）
- POST /v1/responses、洗浄前後の写真各1枚を同一リクエストに渡す。
- JSON Schema準拠のStructured Outputsで受ける（利用モデルの対応確認が前提）。
- モデル名は OPENAI_VISION_MODEL で切り替え可能にする。APIキーはバックエンドにのみ置く。
- store: false を指定。画像は必要な期間のみ保持し、恒久保存を標準としない。
出力スキーマ（概念）：
{
  "before_items": [{"category": "plate", "count": 2}],
  "after_items": [{"category": "plate", "count": 2}],
  "observed_changes": ["食器がシンクから水切りラックへ移動"],
  "washing_evidence": [],
  "alternative_explanations": ["洗わずに移動した可能性"],
  "uncertainties": ["洗浄したかは写真だけでは確定できない"],
  "status": "uncertain",
  "reason": "食器の移動は確認できますが洗浄は判定できません"
}
状態：likely_done、uncertain、not_detected。likely_doneは見た目の推定であり衛生上の保証ではない。視覚的根拠を説明できない場合はuncertainを優先。
5.2 YOLOE（任意追加）
- 候補：YOLOE-26の軽量／小型モデル（利用可能な正確な重みファイル名・ライセンスは実装時に確認）。
- 皿・カップ・ボウル・鍋等をテキスト指定して物体検出／必要ならセグメンテーション。
- Before/Afterごとのクラス・推定個数・bbox・confidenceをOpenAIに参考情報として渡す。
- 食器が消えたことだけをもって洗浄成功としない。
- YOLOEの利用にはUltralyticsのライセンス条件（AGPL-3.0／商用ライセンス）を確認する。
5.3 判定エンジン
1. Beforeに食器が見当たらなければ not_detected。
2. 2画像が重複、極端な遮蔽、解析失敗なら uncertain または not_detected。
3. 明確な洗浄と整合的変化が認められれば likely_done 候補。
4. 食器の移動だけなら uncertain。異なる視角でも無理に断定しない。
5. uncertain の利用者には再撮影または「自分で完了を記録」を提示。
ゲーム上の扱い：自己申告でも同じ基本報酬を付与可能にする。AIに完了認証を過度に担わせない。完了の記録方法（AI推定／自己申告）は内部履歴で区別する。
5.4 評価
90ペアの初期評価（実際に洗浄30、単純移動30、不明瞭30）から開始。写真を再利用して成功と判定させる攻撃的ケースも含める。OpenAI単体・OpenAI+YOLOE・必要に応じ高性能モデルを比較し、誤成功率、検出漏れ、uncertain率、推論時間、コストを記録。複数の台所・照明条件を収集する。
6. ゲームルールと育成
- 1セッション完了につき基本10しずく。1日3回までを初期仮設定。
- 報酬はサーバーがセッション単位で一度だけ確定する（冪等）。
- 池の成長：レベル1（水たまり/0）→2（小池/30）→3（水草/80）→4（花・小魚/150）→5（仲間が出現/250）。閾値は仮置き。
- 洗浄回数が増えてもキャラのかわいさは変化させず、成長の中心は世界・アクセサリー・リアクションに置く。後から進化形を制作する場合もマスターの顔・識別特徴を保持する。
- 小さな1回の成功にもhappy演出を確実に付ける。長期成長は無理な連続ログインを要求しない。
7. API／データ
Endpoint	処理
POST /api/sessions	Before画像受信・セッション生成
POST /api/sessions/{id}/complete	After受信・画像解析・状態更新・報酬付与
POST /api/sessions/{id}/confirm	uncertainの自己申告確定
GET /api/game-state	しずく・池レベル・キャラ状態を取得
GET /api/sessions	セッション履歴取得


主なテーブル：
- sessions(id, started_at, completed_at, status, completion_method, before_detections_json, after_detections_json, ai_analysis_json, reward_granted, reward_amount)
- game_state(id, total_drops, pond_level, last_completed_at)
完了確定・報酬加算・育成状態更新はDBトランザクション内で実行する。ローカル単一ユーザー実証から始め、公開前に認証・ユーザー分離・サーバー側レート制限を追加する。ゲスト識別だけに利用制限を依存させない。
8. 非機能要件
- 画像は撮影時にプレビューし、長辺1280px程度への縮小・EXIF削除を実施。必要最小限の一時保存。
- OpenAI APIキーはバックエンド環境変数。利用者に送らない。
- store: falseは全保持をゼロにする保証ではない。外部送信と保持方針をUIで説明する。
- 画像アップロードの容量上限、形式検証、タイムアウト、リトライ、レート制限。
- AI判定失敗時はエラーでゲームが詰まらず、再試行／自己申告へ戻れる。
- 画像処理の目標P95は8秒以内（未検証）。モデル・ネットワークに応じて再設定。
- アニメーションは遅い端末でもスムーズに。prefers-reduced-motionで動きを抑える代替表現を提供。
- GIFは制作・共有用、ブラウザ再生はスプライトシートPNG+CSS/Canvasで軽量化。

10. 実装フェーズと受け入れ基準
Phase 0 — キャラクターデザイン確定（最優先）
- 4案の静止画を同一サイズで比較。少人数評価と目視レビュー。
- 採用1案のマスターPNG／パレット／アートバイブルを確定。
- 受け入れ条件：同一デザインを誰が再生成しても目・輪郭・色が同じになる。
Phase 1 — キャラクターが「生きている」デモ
- idle / happyのスプライトシートとJSON、ホーム画面、しずくと成長演出。
- ボタンを押すと喜んで池が育つ（AI未接続でも可）。
- 受け入れ条件：ホームを触った瞬間、キャラの反応と育成の魅力が分かる。
Phase 2 — OpenAI + カメラMVP
- Before/After撮影、Responses APIでのJSON判定、再撮影／自己申告、履歴・永続化。
- 受け入れ条件：スマホで食器洗いを完了し、1回だけ報酬が入り、リロード後も保持される。
Phase 3 — 追加モーションとYOLOE
- sleep/grow追加。YOLOEを独立モジュールとして導入し、検出枠表示・画像比較に任意併用。
- 受け入れ条件：マスターの外見を崩さず複数動作が再生でき、YOLOEをオフにしても動作する。
Phase 4 — 評価・公開品質
- 洗浄判定データセット、単体/併用比較、UIユーザーテスト、スマホ性能確認、プライバシー表記。
- 受け入れ条件：技術性能と「育てたいと思うか」を別々に測定し、改善の優先順位を決定できる。
11. 主要リスクと対応
リスク	対応
AI制作のキャラが可愛くない	複数案比較と人間承認を実装ゲートにする
アニメで同じキャラに見えない	マスター、固定パレット、座標・輪郭の検査
判定が誤成功する	uncertainを許容し、衛生的な証明と切り分け
AIの判定待ちで楽しさが薄れる	先に洗浄中の応援を表示、結果まで小演出を挟む
YOLOE併用が遅く高コスト	A/Bで有益性を確認し、不採用可能な設計にする
外部Skill由来の実行リスク	コードをレビューし、秘密情報を渡さない
開発がアート制作だけで長期化	Phase 0は4案→1案に区切り、idle/happyから開始
